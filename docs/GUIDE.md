# rigour guide

This guide covers setup, settings and every command. The [README](../README.md) gives the overview.

On macOS and Linux, type `python3` where this guide shows `py`.

## Setup

### 1. Install the agents

Install [Claude Code](https://code.claude.com) and log in. One Claude account is enough.

Codex is optional. It adds a second model family, so the checks are more independent. Install it with `npm install -g @openai/codex`. Give rigour its own Codex home, so that Codex does not load your global `AGENTS.md`, memories or hooks. Log in there once:

```powershell
$env:CODEX_HOME = "$HOME\.codex-rigour"
codex login
```

If a role uses Codex and Codex is not on the PATH, that role uses the `fallback` agent.

### 2. Add a second Claude account (optional)

A second account adds usage capacity. In PowerShell:

```powershell
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-b"
claude
```

Run `/login` with the second account, then exit. On macOS or Linux, use `CLAUDE_CONFIG_DIR=~/.claude-b claude`. Then set some roles to the `claude-b` agent.

You do not store logins in rigour. Claude Code keeps each login in its config folder. Git keeps its own credentials. Never put passwords or tokens in a settings file or in the records.

### 3. Point rigour at your records

Create `config.json` in the rigour folder:

```json
{ "records": "~/research-records" }
```

The value can be a local folder, a git URL or `gh:owner/repo`. For a git remote, rigour clones the repo to `~/.rigour/<name>`. It pulls before each run, and commits and pushes after each step. Use a private repo.

### 4. Create the records folder

```
py loop.py init
```

This creates `CONTEXT.md`, `TEMPLATE.md`, `ideas/`, `runs/` and `journal/`. Edit `CONTEXT.md` before the first run.

## Settings

rigour reads settings in three layers. A later layer overrides an earlier one:

1. `config.example.json` in the rigour folder. These are the defaults. Do not edit this file.
2. `config.json` in the rigour folder. It needs only `records`.
3. `rigour.json` in the records folder. Put your own settings here, so they travel with your records.

Settings that hold a set of values (`roles`, `agents`, `budget`) merge one level deep. For example, a `rigour.json` that changes only the builder keeps all the other default roles.

| Setting | Default | What it does |
|---|---|---|
| `records` | `~/research-records` | The records folder or git remote |
| `roles` | see the file | The agent, model, effort and skills for each role |
| `agents` | `claude-a`, `claude-b`, `codex` | Each agent's kind (`claude` or `codex`) and its environment variables |
| `fallback` | `{"codex": "claude-b"}` | The agent to use when Codex is not installed |
| `adoption_tracks` | `[]` | Tracks where novelty does not decide anything |
| `scout_survivors` | `3` | The maximum number of ideas that one scout keeps |
| `duplicate_threshold` | `0.35` | The word overlap at which a new idea counts as a duplicate |
| `prior_art` | arXiv, Semantic Scholar, GitHub, 5 each | The search APIs for the pre-check, and the hits per source |
| `budget` | `session_usd` 5, `day_usd` 10 | Spending caps. See [Budgets and usage](#budgets-and-usage). |
| `independence` | `session` | How different the builder and the referee must be |
| `auto_commit` | `true` | Commit and push the records repo after each step |
| `auto_synthesis` | `false` | Run `synthesise` after each session |
| `max_call_minutes` | `60` | The timeout for one agent call |
| `task_name` | `rigour-night` | The name of the scheduled task |

Two environment variables override the files. `RIGOUR_CONFIG` selects a different `config.json`. `RECORDS` selects a different records location.

### Roles

Each role is a separate agent: a fresh, isolated session with its own instructions and no memory of the other roles.

| Role | Default model | Job |
|---|---|---|
| `scout` | Sonnet | Generates ideas and drops the ones with clear prior art |
| `precheck` | Sonnet | Searches the free APIs with its own queries and stops ideas with a clear match |
| `novelty1`, `novelty2` | Sonnet, Opus | Two independent prior-art checks |
| `tiebreak` | Opus | Decides when the two checks disagree |
| `triage` | Sonnet | Decides if a build is worth the time |
| `referee_spec` | Sonnet | Writes the criteria and the sealed tests |
| `builder` | Sonnet | Builds the MVP from the criteria |
| `referee_judge` | Opus | Runs the tests and writes the verdict |
| `synth` | Sonnet | Writes the session journal |

Use `"model": "default"` for Codex's default model. To skip the pre-check or triage, remove that role from `roles`.

### Independence

The `independence` setting controls how different the builder and the referee must be:

| Value | The builder and the referee must differ in |
|---|---|
| `session` | Nothing more. Separate sessions are enough. |
| `model` | Model or account |
| `account` | Account, or CLI such as Codex |

A stricter level reduces correlated mistakes. LLM judges tend to prefer output from their own model ([Panickssery et al. 2024](https://arxiv.org/abs/2404.13076)). The sealed tests limit this effect, because the referee writes its tests before it sees the build. The strongest setup uses Codex as the referee and the second novelty check, with Claude as the builder.

## Tracks

`CONTEXT.md` tells the agents what to look for. It has shared sections (goals, edge, rules) and optional tracks. A track is a section with the heading `## Track: <name>`. The name is one word that you choose.

Put a track name first in a command to research only that track:

```
py loop.py auto 5 work
py loop.py scout work ideas about invoice automation
```

The scout gets the shared sections and that one track, and it tags each idea with the track name. The session then tests only ideas with that tag. Without a track name, the scout can use all tracks.

On a normal track, novelty decides: an idea that already exists stops after the novelty stage. On an adoption track, the value to a team decides. List those tracks in `adoption_tracks`. Their ideas skip the novelty stage and go straight to triage.

## How a run works

`py loop.py run <idea-id>` tests one idea in these steps:

1. Novelty. First, the pre-check searches the free APIs. One Sonnet call reads the hits and can rerun the search with better queries. A clear match stops the idea here. Otherwise, two agents search for prior art in separate sessions. Both get the same hits as a head start. If they disagree, the tie-break model decides. An idea that exists stops here.

   Adoption tracks skip this step.
2. Triage. One Sonnet call reads the idea, the track's criteria and the novelty results. It decides if a build would teach anything new. For a large project, it judges one slice of the first milestone.
3. Referee spec. The referee writes `criteria.md`, `holdout.md` and pytest tests. The tests go in `.sealed/`, outside the builder's folder.
4. Build. The builder gets the criteria, the related records and up to two related earlier MVPs. It never sees the tests.
5. Judge. The referee checks the hash of its tests, runs them, reproduces the result and writes `verdict.json`.
6. Record. rigour adds a dated line to the idea, sets its status, rebuilds the index and commits.

Before any of this, the scout step drops near-duplicate ideas. It compares the words of each new idea with the existing records. It uses no LLM.

## Free prior-art search

`search.py` queries public APIs with no LLM. It builds the query from the idea's title. If an AND-style search finds nothing, it drops keywords and tries again. If a source fails or hits a rate limit, rigour skips it and the run continues.

| Source | Key | Environment variable |
|---|---|---|
| arXiv | not needed | none |
| Semantic Scholar | optional, raises the rate limit | `S2_API_KEY` |
| OpenAlex | needed for more than a few calls a day | `OPENALEX_API_KEY` |
| GitHub repositories | optional, raises the rate limit | `GITHUB_TOKEN` |

Put keys in environment variables only, never in a settings file. Without keys, the search covers little outside computer science and physics: arXiv has few economics papers, and the keyless Semantic Scholar pool is often rate-limited. For economics and business topics, get the free Semantic Scholar and OpenAlex keys and add `openalex` to the sources. Set `"sources": []` to turn the search off. To add OpenAlex, list it in `prior_art.sources`. To try a search by hand, run `py search.py "<title>"`.

The pre-check says "exists" only when a hit delivers the core feature itself. A paper that describes a method does not count as software that implements it. The pre-check misses new or niche packages, because PyPI has no search API. The agent search catches those. Canaries record the pre-check's catch rate under `precheck/<model>`.

## Sessions and scheduling

```
py loop.py night 120 [track] [topic]   # start new work for 120 minutes
py loop.py auto 5 [track] [topic]      # run 5 cycles
py loop.py schedule 01:00 120          # every night at 01:00, for 120 minutes
py loop.py unschedule
```

A session follows these steps:

1. It rebuilds the digest and the search index. This step uses no LLM.
2. It runs cycles. Each cycle tests the oldest untested idea. If fewer than two ideas wait, the scout runs first. Every third cycle runs a canary. A failed run parks its idea, and the session continues.
3. It writes a report to `journal/` and commits the records.

`night` starts new ideas only before the time is up. The idea in progress always finishes. `auto` counts cycles and has no time limit.

`schedule` uses Windows Task Scheduler. On macOS and Linux, it prints a cron line for you to add. The computer must be on, awake and logged in at that time. The log goes to `logs/<task_name>.log`.

To continue a partial run, use `py loop.py resume <idea-id>`. rigour copies the last MVP and adds regression tests for the reported defects. The builder then tries one repair.

## Budgets and usage

Set caps in the `budget` setting:

```json
"budget": { "session_usd": 5, "day_usd": 10, "five_hour_pct": null, "seven_day_pct": null }
```

rigour checks the caps before it starts new work. `null` turns a cap off.

- `session_usd` and `day_usd` use the USD-equivalent that Claude Code reports at list prices. On a subscription, this measures usage and is not a bill. Codex reports no cost, so these caps count Claude calls only.
- `five_hour_pct` and `seven_day_pct` stop new work when an account reaches that share of its subscription limit.

If an account reports that it reached its limit, the session stops at once. The idea in progress stays untested and goes first next time.

```
py loop.py usage        # the last logged usage per account
py loop.py usage now    # a fresh reading, from one small call per account
```

`metrics.csv` logs every call: role, agent, model, cost, tokens, web searches and seconds. rigour runs with `--no-session-persistence`. Tools that read Claude Code's session logs, such as ccusage, do not see its calls.

## Canaries and calibration

A canary is an idea that the records already mark as dropped because it exists. `py loop.py canary 3` removes the prior art and the lessons from three such ideas. Then it asks each novelty agent about them. A correct agent answers "exists".

`py loop.py calibration` prints the catch rate for each agent and model. Canaries measure missed prior art only. They do not measure false alarms on new ideas.

## How agents get context

Each agent gets a small, fixed set of files:

1. `DIGEST.md` has one line for each idea. A script builds it.
2. `RELATED.md` has the top 5 matches for the task from a local BM25 index. It holds about 1500 characters. rigour also adds one line for each idea that `graph.json` links to those matches.
3. `related/` holds copies of up to two related earlier MVPs. Only the builder gets it.

No agent gets the full history. Dropped ideas and failed runs stay in the index, so their lessons come back when a similar idea appears.

## Records layout

| Path | Contents |
|---|---|
| `CONTEXT.md` | Goals, tracks, your edge and the rules |
| `rigour.json` | Your settings (optional) |
| `TEMPLATE.md` | The format of an idea file |
| `ideas/<id>.md` | One idea: status, problem, prior art, dated progress, lessons |
| `runs/<date>-<id>/` | Novelty results, triage, the MVP, the verdict and `result.json` |
| `DIGEST.md`, `INDEX.md`, `graph.json` | One line per idea, ideas by status, links between ideas |
| `journal/` | One report per session |
| `metrics.csv` | One row per agent call |
| `calibration.csv` | One row per canary per agent |
| `search.sqlite` | The BM25 index. rigour rebuilds it, so git ignores it. |

To search the records yourself, use `py records.py search <records-folder> "<query>"`.

## Several instances

You can run separate instances, for example one for personal research and one for work. Each instance has its own records repo. Make a second config file with its own `records` and `task_name`, and select it with `RIGOUR_CONFIG`:

```powershell
$env:RIGOUR_CONFIG = "C:\path\to\config-work.json"
py loop.py schedule 02:00 60
```

The scheduled task keeps this setting.

If a records folder links to repos on a host other than GitHub, add `links.json` to that folder, for example `{"gitea": "https://git.example.com/"}`. Then `gitea:owner/name` links pass the link checks.

## Safety and terms

- Give the loop free, public data only. Never give it credentials or licensed data.
- Every call runs with `--safe-mode` (none of your CLAUDE.md, memory, hooks or plugins) and `--restricted` (file tools stay in the working folder).
- The builder can still run Python, and Python can read any file. Run rigour on a machine where that is acceptable, or in a container.
- Codex's `workspace-write` sandbox limits writes but not reads. A Codex builder could read the sealed tests, so use Codex as a referee.
- Anthropic allows `claude -p` in your own scripts. Check the current terms for your plan. Use one account per person, and do not share or resell access.
